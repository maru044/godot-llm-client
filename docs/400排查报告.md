# deepseek-v4-flash 400 排查报告

> 场景：阶段1 连通性测试，用 `deepseek-v4-flash`（用户真实 API key）跑通对话时返回 HTTP 400。
> 结论：**根源不是 max_tokens，也不是端点，而是 DeepSeek V4 默认「深度思考模式(Thinking Mode)」与带 `<thinking>` 开头的 Prefill + tools 的组合冲突。新增 `"thinking": {"type": "disabled"}` 一条即可解决。**

---

## 一、结论先行

你确认过：`max_tokens` 没问题，`deepseek-v4-flash` 输出上限远大于 65536。实测证实这一点，真正诱因是 **Thinking Mode**.

| 组合 | 结果 | 说明 |
|------|------|------|
| 无 prefill + 有 tools | ✅ OK | 无 Prefill 时不触发思考链校验 |
| 有 prefill + 无 tools | ✅ OK | 有 Prefill 但无工具时也能过 |
| **有 prefill + 有 tools** | ❌ 400 | 三者同时存在 → 触发 `reasoning_content` 校验 |
| **加上 `thinking:disabled` 后（有prefill+有tools）** | ✅ OK | 关闭思考模式即绕开 |
| `thinking:disabled` + `max_tokens:65536` | ✅ OK | 65536 完全没问题 |

---

## 二、错误信息（原始）

```
{"error":{"message":"The `reasoning_content` in the thinking mode must be passed back to the API.","type":"invalid_request_error","code":"invalid_request_error"}}
```

---

## 三、根因

DeepSeek V4 全系列（含 `deepseek-v4-flash`）**默认开启 Thinking Mode**。

在思考模式下做**前缀续写(prefill)** 时，API 的网关校验要求：如果模型已进入思考链，那么对话历史里靠后的 assistant 消息必须用 `reasoning_content` 字段把思考内容完整回传，否则无法对齐，直接 400。

我们的 Prefill 是 `</think>\n<thinking>\nOK，超级歌姬上线...`，它让最后一条 assistant 消息以"思考"序列开头，但又**没有**标准 `reasoning_content` 字段。而当同时启用 `tools` 时，这个校验被真正触发（无 tools 时 DeepSeek 放过了）。

所以：**问题不在 Prefill 内容本身（内容仍是 Miku 反应，没动），而是它「以 thinking 序列开头」+「thinking 模型 + tools」三者叠加，触发校验**。

---

## 四、为什么「只加 thinking:disabled」就够（不用加 /beta、不用加 prefix）

搜索资料建议的三点：
1. `"thinking": {"type": "disabled"}` ✅ **实测有效**（三选一里真正管用的）
2. 走 `/beta/chat/completions` ❌ **实测不需要**，默认端点即可
3. 最后一条 assistant 加 `"prefix": true` ⚠️ 实测是非必需的（`thinking:disabled` 已让校验不再触发）

> 结论：**`thinking:disabled` 是唯一必要修改**，且它放在请求体顶层，对不支持该字段的模型(如 Gemini 中转)应会被忽略或无害——需要实测确认，这是你要"各模型统一逻辑"的关键。

---

## 五、推荐方案：各模型统一逻辑

为了避免每个模型拼不同报文，建议在 `LLMClient` 里做一个**通用开关**，而不写死：

- 把 `thinking_enabled` 作为可配置项（读自 `ConfigManager`）。
- **DeepSeek V4 等 thinking 模型 → `thinking_enabled = false`**（因为我们的 prefill 是普通 content 引导，不打算配合思考链回传）。
- **Gemini 等非 thinking/中转模型 → `thinking_enabled = true` 或不注入**（保持原样）。

```gdscript
# LLMClient._trigger_react_loop 内，构 payload 前
if _disable_thinking:   # 由 ConfigManager 或模型名推断
    payload["thinking"] = {"type": "disabled"}
```

判断依据可复用 `ConfigManager.supports_vision`：当前 `deepseek-v4-flash` 的 `supports_vision=false`，`gemini` 为 `true`。可用 `not supports_vision` 作为"开启 thinking-disabled"的启发式，但它不够精准；更稳的是在 `config_manager.gd` 预置里为每个模型显式加一个 `thinking_disabled: bool` 字段。

---

## 六、下一步动作

1. `ConfigManager.presets` 为每个预设加 `thinking_disabled` 字段（`deepseek: true`, `gemini: false`, `custom: 默认 false`）。
2. `ConfigManager.apply_preset` / `load_config` 读取该字段，暴露 `var thinking_disabled: bool`。
3. `LLMClient._trigger_react_loop` 构建 payload 时，若 `ConfigManager.thinking_disabled` 为真，注入 `payload["thinking"] = {"type": "disabled"}`。
4. 重新跑连通性测试，确认 DeepSeek 能收到真实回复。

> 这样 **Gemini / DeepSeek 共用同一套 Prefill（Miku 反应）+ 同一套 ReAct 循环**，只通过一个开关适配 thinking 模型，符合"各模型沿用一样逻辑"。
